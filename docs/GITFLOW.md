# Gitflow в этом проекте

Как устроена история и как работать дальше.

## Ветки

```
main ───●──────────●───────────●──────►  10 релизов, 10 тегов
         ╲        ╱ ╲         ╱
dev ──────●──●───●────●───●──●────────►  13 мержей, интеграция
           ╲╱          ╲╱
feature/* ─●────────────●─────────────►  работа над фичей
```

| Ветка | Назначение | Кто вливает |
|---|---|---|
| `main` | только релизы, теги `v0.x.y` | `dev` через релизный PR |
| `dev` | интеграция, здесь проверяется всё вместе | `feature/*` через PR |
| `feature/*` | одна задача | автор, после ревью |

**Напрямую в `main` не коммитим никогда.** Даже однострочный фикс.

## Как работать

```bash
# 1. Ветка от dev
git checkout dev
git pull
git checkout -b feature/kratkoe-imya

# 2. Работа
git add -A
git commit -m "тип: что сделано"

# 3. Пуш и PR
git push -u origin feature/kratkoe-imya
```

Дальше — PR в `dev` на GitHub. После ревью и зелёного CI — merge.

Релиз: PR `dev` → `main`, тег на получившийся коммит.

## Типы коммитов

| Префикс | Когда |
|---|---|
| `feat:` | новая возможность |
| `fix:` | исправление |
| `docs:` | документация |
| `ci:` | настройка проверок |
| `chore:` | служебное, без изменения поведения |
| `speed:` | оптимизация |
| `eval:` | метрики качества |
| `tracing:` | наблюдаемость |

Сообщение — что изменилось для пользователя, а не «обновил файл X».

## Версии

`v0.MINOR.PATCH`, все `0.x` — проект до первого стабильного релиза.

- **MINOR** — новая возможность
- **PATCH** — исправление

**Нумерация идёт вперёд во времени, а не по смыслу.** Если патч вышел
после релиза `v0.3.0`, он станет `v0.3.1`, а не `v0.2.1` — даже если
правит код из `v0.2.0`. Иначе в истории версия идёт назад, и непонятно,
что новее.

### Первый честный цикл

`v0.11.0` — первый релиз, прошедший полный путь без переписывания
истории: ветка `feature/design-polish` → PR #16 → `dev` → PR #17 →
`main` → тег. Дата мержа настоящая, PR видны в GitHub, ветка удалена
после мержа.

Дальше так каждый раз. Правило простое: если после работы хочется
закоммитить прямо в `main` — значит, забыли создать ветку.

## Про переписывание истории

История собрана задним числом: 26 коммитов лежали в `main` подряд, и их
разложили по 13 веткам с мержами и релизами.

**Что сохранено:** даты коммитов (авторства и создания), их тексты и
содержимое файлов. Дерево `main` совпадает с оригиналом байт в байт.

**Что проставлено автором:** даты мержей и релизов. Git позволяет задать
любую дату коммита — и это ровно та причина, по которой по датам в git
нельзя судить, кто что сделал и когда.

**Чего не получилось:** PR. GitHub создаёт PR только на незалитую ветку,
а мерж через API ставит сегодняшнюю дату. Совместить исходные даты и
настоящие PR на готовой истории невозможно — попытка заняла несколько
итераций и выяснилась на практике.

Поэтому: структура веток и релизов настоящая, PR — нет.

## Инструменты перевода истории

Раздел про одноразовую операцию — переписывание истории с 26 коммитов под
gitflow. Для текущей работы эти скрипты не нужны, они остались как отчёт
о том, как это было сделано.

| Файл | Назначение |
|---|---|
| `plan.ts` | план: какие коммиты в какие ветки, тексты PR и релизов |
| `verify.ts` | сверка плана с историей **до** переписывания |
| `reorder.ts` | перестановка блоков плана |
| `final.ts` | сборка истории с мержами и датами |
| `rebuild.ts` | сборка веток без мержей (для PR) |
| `build.ts` | первая версия сборки |

Запуск: `node scripts/gitflow/verify.ts`

Сверка поймала две реальные ошибки в плане: коммит-фикс стоял в ветке
раньше кода, который правит, и версии шли назад. Обе — до необратимого
шага. Поэтому `verify.ts` запускать обязательно.

## Инструменты ежедневной работы

| Файл | Назначение |
|---|---|
| `pr.ts` | создать PR из текущей ветки в `dev` (или базовую из `BASE_BRANCH`) |
| `merge-pr.ts` | смержить PR по номеру: `node scripts/gitflow/merge-pr.ts 16` |
| `release-pr.ts` | релизный PR `dev → main`: `node scripts/gitflow/release-pr.ts "Release: …"` |

Токен читается из `GH_TOKEN`, а не из аргументов: аргументы видны в
истории команд, переменная окружения — нет.

```powershell
$env:GH_TOKEN = (Get-Content "$env:TEMP\gh_token" -Raw).Trim()
node scripts/gitflow/pr.ts "заголовок" "описание"
```

`merge-pr.ts` сначала проверяет `mergeable`: если GitHub ещё не посчитал
статус, PR будет помечен как «не мержится», хотя конфликтов нет. Скрипт
ждёт пересчёта, а не мержит вслепую.
