# Как работает VentilationProposalService

Полный разбор: какие технологии применены, зачем именно они и как всё
связано между собой. Это не список «что мы выучили», а объяснение
приложения от входа до выхода — с причинами решений и с тем, что
сломалось по дороге.

---

## Что делает приложение

Клиент присылает смету — список строк вроде «Воздуховод круглый 315,
10 м» или «Тройник 315х200, 3 шт». Сервис:

1. Разбирает строки и находит каждую позицию в прайсе из 215 позиций.
2. Считает суммы **только для тех позиций, что есть в прайсе**.
3. Формирует коммерческое предложение в DOCX.
4. Отвечает на вопросы клиента в чате — но только про это КП.
5. Отдаёт новые КП внешней автоматизации (n8n), которая уведомляет
   менеджера в Telegram и напоминает о сделках без ответа.

Главное правило: **ошибочная цена опаснее отсутствия цены**. Если
матчинг не уверен — позиция остаётся без цены и помечается «уточнить
у менеджера». Менеджер получает «нет цены», а не «цена 606 ₽» там, где
на самом деле 6 060 ₽. Первое — рабочая ситуация, второе — убыток
и потерянный клиент.

## 1. Парсинг и нормализация

**Файл:** `src/lib/price/normalize.ts`

Строка клиента хаотична. В реальном прайсе встречается:

- «Воздуховод круглый d315», «воздуховод ⌀315», «Воздуховод 315»
- «Тройник 315х200» и «Тройник 315-200» — тот же размер
- «Отвод 90°» и «Отвод 90 градусов»
- «Спиральный воздуховод» и «воздуховод спиральный»

`normalize()` приводит всё к канону: нижний регистр, единая раскладка,
размеры через `/`, синонимы по типам.

**Ловушка, на которой всё ломалось:** JavaScript `\w` и `\b` не понимают
кириллицу. `\bвоздуховод\b` не сработает для «воздуховод», потому что
`в` не считается словесным символом. Решение — явные диапазоны
`[а-яё]` и `(?:^|[^а-яё])`.

**Вторая ловушка:** дефис как разделитель размеров. «Тройник 315-200»
и «Тройник 315-200-100» — оба валидны, но «Отвод 90-250» — угол и
диаметр. Правило заменило дефис на `/` только между числами, где обе
части — размеры:

```js
s = s.replace(/(?<=\d)\s*[-—–]\s*(?=\d{2,4}(?!\d))/g, "/")
```

**Третья ловушка:** голое «отвод» без параметров неоднозначно. Может быть
отвод 45° или 90°, сегментный или штампованный — цены разные. Правило
возвращает `unknown` и отправляет на LLM, а не угадывает.

## 2. Матчинг: детерминизм → LLM → человек

**Файл:** `src/lib/matcher/hybrid.ts`

Три уровня, в порядке возрастания стоимости и убывания надёжности:

```
Точное совпадение ключа       ~90% строк, 0 мс, 0 ₽
        ↓ не нашли
Гибридный поиск + LLM         ~8% строк, ~800 мс, копейки
        ↓ не уверены
Человек уточняет              ~2% строк
```

**Почему LLM не решает всё.** LLM ошибается тихо: ответ выглядит
уверенно и правдоподобно. Детерминированный матчинг ошибается только
там, где нормализация не справилась, — и это видно по критерию. Там где
можно решить кодом, код и решает.

**Порог уверенности:** `CONFIDENCE_THRESHOLD = 0.85`. Ниже — позиция
уходит человеку, а не в КП с приблизительной ценой.

**Ключевое архитектурное решение:** LLM никогда не называет цену. Он
возвращает только `priceId` — идентификатор позиции прайса. Цену
подставляет код из прайса. Даже если модель «выдумает» цену, ей негде
её записать: в инструментах нет такой возможности.

## 3. RAG: поиск по прайсу через pgvector

**Файлы:** `src/lib/rag/embed.ts`, `search.ts`, `hybrid.ts`

Когда детерминированный матчинг не справился, нужен поиск «похожего
по смыслу». Здесь работает RAG.

### Как устроено

1. Каждая позиция прайса превращается в вектор 1024 числа через
   `baai/bge-m3` — модель, которая понимает русский и работает с
   короткими техническими названиями.
2. Векторы лежат в Postgres в колонке `vector(1024)`, поиск по
   косинусному расстоянию через индекс.
3. При запросе: текст клиента → вектор → поиск ближайших позиций
   → результат отдаётся LLM как контекст.

### Почему гибридный поиск, а не чистые вектора

Чистый векторный поиск проваливается на числах. «Отвод 250» и «Отвод
300» семантически почти одинаковы — для модели это «отвод» плюс размер,
а размеры близки. Но разница в цене существенна.

Поэтому `hybrid.ts` смешивает два сигнала:

```
итоговый счёт = 0.55 × косинусное сходство + 0.45 × совпадение слов
```

Веса подобраны так, чтобы числа (диаметры, углы) влияли сильно.
Ключевое слово «315» в строке даёт почти точное попадание в размер.

### Почему RAG — добавка, а не решатель

RAG помогает найти кандидатов, но **не решает**, какая цена верна.
Решение принимает детерминированный матчинг или человек. Если бы RAG
решал, «Отвод 250» мог бы получить цену от «Отвода 300» — и никто бы
не заметил.

### Что дал замер

| Показатель | Значение |
|---|---|
| Минимум | 608 мс |
| Медиана | 887–1170 мс |
| Максимум | ~6800 мс |

Максимум — не наш код, а пулер Neon: он изредка «зависает» на 5 секунд.

## 4. Postgres: почему не in-memory и не Mongo

**Файлы:** `src/db/schema.ts`, `connection.ts`, `repositories/*`

Начиналось с `Map` в памяти. Умерло на первом же запросе после деплоя:
Vercel поднимает несколько инстансов функции, и каждый видит свою копию
`Map`. Клиент загрузил смету — второй запрос попал в другой инстанс —
сметы нет.

### Схема

**`price_items`** — прайс, 215 позиций. Загружается один раз, кэш 5 минут.

**`estimates`** — снимок КП. Хранит сумму, количество позиций,
`notified_at` (когда отдали автоматизации), `expires_at` (24 часа).

**`estimate_positions`** — позиции с **копией цены**, а не ссылкой.
Если прайс завтра изменится, старое КП не должно «пересчитаться»:
клиенту уже назвали цену.

**`proposal_log`** — журнал сделок без срока жизни: клиенты
возвращаются через недели, история нужна дольше, чем живёт документ.

### Решение: деньги в `numeric`, не `float`

```ts
totalSum: numeric("total_sum", { precision: 14, scale: 2 })
```

`float` в JS — двоичная дробь. `0.1 + 0.2 !== 0.3`. В смете из 100
позиций накопленная ошибка даёт расхождение в рублях, и клиент увидит
«21 010.000000001 ₽». `numeric` в Postgres — точная десятичная
арифметика.

### Ловушка Neon, которая ломала всё

Пулер Neon (PgBouncer) рвёт соединение после нескольких тяжёлых
запросов. Симптом: второй векторный запрос висит 19 секунд, третий
лёгкий — 70 секунд.

Решение в `connection.ts`:

```ts
const MAX_OPS_PER_CONNECTION = 1
```

Одна операция на соединение, потом переподключение. Медленнее в теории,
но стабильно на практике. Плюс `withRetry` с экспоненциальной паузой.

**Урок:** проблема была не в нашем коде. Прямой запрос без обёрток тоже
иногда давал 5308 мс. Это поведение пулера, и его надо обходить, а не
«оптимизировать».

### Второй лимит того же пулера: размер параметра

Пока не пришлось писать векторы, мы думали, что знаем про этот пулер всё.
Оказалось, у него есть ещё один порог — на размер одного параметра
запроса. Это самый дорогой по времени поиск бага в проекте, и он стоит
того, чтобы записать выводы.

**Симптом.** `insert … values (…, $1::vector)` и `update … set embedding =
…` висят 19-25 секунд и падают:

```
write CONNECTION_CLOSED ep-damp-cloud-…pooler.…
  cause: Error: read ECONNRESET
```

Воспроизводимость 3 из 3, стабильно. Не зависит ни от индексов (падало и
на пустой таблице без единого индекса), ни от размера таблицы, ни от
драйвера, ни от `idle_timeout`/`statement_timeout`.

**Что пробовали и что не помогло** — важно, потому что половина этих
«решений» выглядит логично:

| Гипотеза | Проверка | Итог |
|---|---|---|
| Транзакции | `delete` + `insert` по отдельности | та же ошибка |
| Устаревшее соединение | `connectOnce` на каждую запись | та же ошибка |
| HNSW-индекс мешает | вставка в пустую таблицу без индексов | та же ошибка |
| Мусор в таблице | `vacuum analyze` | та же ошибка |
| Другой драйвер | `pg` вместо `postgres.js` | та же ошибка |
| Hex-упаковка `float4` | 8192 символа, ниже порога | запрос мал, но распаковка в SQL упирается в таймаут 60 с |
| `insert … on conflict do update` | upsert вместо update | та же ошибка |

**Настоящая причина — размер.** Замер по шагам, меняя только число знаков
в значениях вектора:

| Размер параметра | Что внутри | Результат |
|---|---|---|
| 4097 байт | 1024 значения по 1 знаку | 35 мс, ок |
| 8193 байта | по 5 знаков | 36 мс, ок |
| 13 313 байт | по 10 знаков | обрыв через 19 с |
| 21 682 байта | реальный вектор `bge-m3` (f64) | обрыв через 19 с |

Порог где-то между 8 и 13 КБ. Вектор из 1024 чисел в полной точности
`float64` — это 21 682 байта, то есть вдвое больше допустимого.

**Решение: округление.** Вектор `bge-m3` нормализован, значения лежат в
диапазоне примерно -0.15…0.20. Пять знаков после запятой дают
погрешность ≤ 5e-6 на компоненту, и строка сжимается с 21 682 до
~8 600 байт — ниже порога. Проверено: 3 из 3 векторов записываются за
247-276 мс вместо обрыва.

Что это значит для качества поиска: косинусное расстояние меняется в
шестом знаке. Разница между «похоже» и «не похоже» — это сотые, так что
округление не влияет ни на что. Зато `embedded_at` теперь реально
записывается.

**Ещё одна ловушка того же расследования:** `pg` висит ~70 секунд на
`client.end()`, потому что пулер не отвечает на `Terminate`. Две позиции
превращались в 139 секунд при 260 мс собственно записи. Лечится тем, что
закрытие не ждут: `void client.end().catch(() => {})`.

Код — `src/db/vectorWriter.ts`, там же подробные комментарии.

**Урок:** «не работает только это» — плохой диагноз. Здесь он держался
часы, потому что я проверял *способы записи*, а надо было замерить
*размер параметра*. Один замер порога по бисекции заменил бы всё
расследование.

### Свой прайс у каждого клиента

`price_items.org_id` — прайс принадлежит организации. Уникальность по
паре `(org_id, code)`, а не по коду: у двух клиентов может быть позиция
с одним кодом и разной ценой. Миграция — `scripts/apply-migration-0005.ts`.

Загрузка (`POST /api/price/upload`) заменяет прайс целиком: если
поставщик убрал позицию, она должна исчезнуть, а не остаться со старой
ценой. Гость править прайс не может (403), демо-организация тоже.

Векторы пишутся **после** ответа клиенту, через `waitUntil`. Загрузка не
ждёт эмбеддингов: 215 позиций загружаются за 1.3 с, индексация идёт
2-3 с в фоне. Если провайдер эмбеддингов недоступен, прайс всё равно
работает — точный матчинг по типу и размерам от векторов не зависит.

## 5. Агент на LangGraph

**Файлы:** `src/lib/agent/graph.ts`, `tools.ts`, `ragTool.ts`

### Граф

```
      guard (проверка темы)
            │
     ┌──────┴──────┐
     │             │
  не по теме    по теме
     │             │
  refuse        agent ──► tools ──► agent (цикл)
                   │
                   ▼
                 ответ
```

`guard` — детерминированная проверка: вопрос про погоду не дойдёт до
LLM. Это экономит деньги и убирает класс проблем: модель, отвечающая
на любой вопрос, рано или поздно ответит не то, что нужно.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `search_price` | Гибридный поиск по прайсу (RAG) |
| `get_estimate` | Текущая смета клиента из сессии |
| `get_position` | Одна позиция с деталями матчинга |
| `explain_absence` | Почему позиции нет в прайсе |
| `calc_total` | Сумма по позициям с ценой |
| `find_similar` | Похожие позиции |
| `get_pricelist_info` | Единицы измерения, правила |

**Набор инструментов зависит от вопроса.** `toolsFor(text)` отдаёт
только релевантные: вопрос про сумму не получает доступ к поиску по
прайсу. Меньше инструментов — меньше токенов и меньше шансов, что
модель вызовет не тот.

### Ловушка: `ToolNode` должен получить ВСЕ инструменты

```ts
const toolNode = new ToolNode(allTools)
```

`ToolNode` выполняет вызовы, которые модель вернула. Если передать ему
только часть инструментов, модель вызовет отсутствующий — и узел
упадёт. Набор ограничивается не здесь, а тем, что видит модель на
входе.

### Потоковый ответ и шаги вместо «Думаю…»

Агент отвечает 4-8 секунд. Раньше всё это время пользователь видел одно
слово «Думаю…»: непонятно, работает система или повисла. Теперь `/api/chat`
отдаёт Server-Sent Events, а в чате идёт список шагов.

```
event: step   {"id":"agent","label":"Смотрю прайс и считаю","status":"start"}
event: step   {"id":"agent","label":"Смотрю прайс и считаю","status":"done","ms":3193}
event: done   {"ms":6830,"tokens":2305,"toolCalls":0,"answer":"Ниппель … 221 ₽/шт."}
```

**Почему не `streamEvents`.** Он отдаёт внутренности LangGraph — узлы,
состояния, служебные сообщения. Наружу это выдавать нельзя: там видны
имена инструментов и промежуточные данные прайса. Поэтому поток
разбирается в `api/chat/stream.ts` и превращается в узкий контракт из
трёх событий. В события не попадает ничего, чего нет на экране.

**Ловушка, на которой я попался.** Первая версия сопоставляла шаги с
именами *инструментов* (`rag`, `estimate`), а `stream()` отдаёт имена
*узлов графа* (`guard`, `agent`, `tools`). Ключи не совпали, и
пользователь не увидел ни одного шага — молчаливо, без ошибки.
Диагноз дал прямой тест `streamAgent` вне HTTP: он показал
`guard:start, agent:start, tools:start, agent:done`, то есть шаги есть,
просто фильтр их выкидывал.

**Текст пока не режется на токены.** Это осознанно: узел `agent` внутри
сам вызывает модель через `invoke`, и токенного потока из него нет.
Слайс по символам был бы имитацией стриминга. Настоящий прогресс здесь —
шаги, а не постепенное появление букв. Переписать узел на `model.stream`
можно (это следующий шаг), но там надо склеивать фрагменты и заново
собирать `tool_calls` — риск выше пользы, пока шаги уже решают задачу
«видно, что происходит».

**Порядок записи.** История и токены пишутся в `start` потока *после*
`controller.close()`: пользователь уже увидел ответ, и задерживать его
ради записи в базу незачем. Если запись не удастся, ответ останется
верным — потеряется только контекст следующего вопроса.

## 6. Защита от prompt-injection

**Три уровня, и они независимы:**

**Уровень 1 — архитектурный.** У агента нет инструмента, который
меняет цену. Даже полностью управляемая модель не может назвать свою
цену: она возвращает `priceId`, сумму считает код.

**Уровень 2 — промпт.** Пользовательский текст оборачивается в
разметку, а инструкция «игнорируй предыдущие указания» попадает в
данные, а не в команды.

**Уровень 3 — код.** `validate()` проверяет ответ модели на
запрещённые паттерны. `guard` отсекает вопросы не по теме до LLM.

**Проверка:** 5 атакующих кейсов в датасете — попытки установить цену,
вытащить промпт, сменить роль. Результат **5/5 отражено**, ни одного
ложного срабатывания.

## 6.5. Обратная связь менеджера: замкнутый круг

**Файлы:** `src/lib/matcher/synonyms.ts`,
`src/db/repositories/matchFeedback.ts`, `src/features/review-match/`

### Проблема, которую это решает

Система честно отказывается ставить цену, когда совпадение неоднозначное.
Такие строки разбирает человек. Но разбор уходил вместе с менеджером: он
правил КП и закрывал вкладку, а система в следующий раз спотыкалась о то
же слово. Опыт терялся.

### Как работает круг

```
смета ──► строка не нашлась ──► менеджер подтверждает
                                        │
                                        ▼
                              пара «формулировка → код»
                                        │
                                        ▼
                            словарь синонимов организации
                                        │
        следующая смета ◄───────────────┘
        (цена находится сама)
```

В интерфейсе это кнопка «Подсказать правильную позицию» на строках без
цены. Сохраняется пара «как написал клиент → код позиции прайса» в таблице
`match_feedback`.

### Где именно применяются синонимы

**До матчинга, а не после.** `rewriteWithSynonym` переписывает строку
сметы на название из прайса, и только потом запускается обычный
детерминированный матчинг. Если применять после, строка уже получила
статус `not_found`, и «дотягивать» её значит спорить с результатом.
Переписывание на входе — не спор, а уточнение входа.

`matchLine` при этом остаётся чистой функцией: строка и прайс на входе,
результат на выходе, ни базы, ни сети. Это её главное достоинство —
проверяется без окружения и не зависает от сетевой ошибки.

### Три ошибки, которые нашлись тестами

**1. Слишком короткие синонимы.** Первая версия отбрасывала фразы короче
трёх символов. Тест показал: «отв» (три символа) проходит порог, а это
стандартное сокращение от «отвод». Приняв его за синоним к конкретной
позиции, мы переписали бы ЛЮБОЙ отвод в один код, независимо от типа и
размеров. Порог поднят до четырёх.

**2. `on conflict` не работает с `null`.** Уникальный индекс
`(org_id, estimate_id, pos_no)` не срабатывает, когда `estimate_id` равен
`null`: в Postgres `null` не равен `null`. Вторая правка создавала новую
строку вместо обновления, и словарь считал бы один случай дважды. Для
записей без сметы сделана отдельная ветка: сначала поиск, потом вставка.

**3. Дублирование размера.** Строка «Воздуховод спиральный 315» после
замены превращалась в «Воздуховод спирально-навивной 315, м.п. 315».
Разбор количества принимал второй «315» за количество — в смете
появлялось «315 штук». Нашлось сквозным тестом, а не юнит-тестом: юниты
проверяли замену, но не её последствия для соседних шагов.

Правило чистки получилось неочевидным: из названия убирается размер,
который **есть в строке**, а не все размеры позиции. Если менеджер
сопоставил «315» с позицией «400», размер «400» убирать нельзя — это
размер самой позиции, и без него название станет неверным. Лучше лишний
размер, чем потерянный.

### Проверки

`test-synonyms.ts` (23) — края замены: границы слов, регистр, порядок
фраз, дубли размеров. `test-feedback.ts` (13) — API, изоляция
организаций, идемпотентность. `test-feedback-loop.ts` (8) — сквозной
круг: смета → разбор → смета находит цену.

### Почему не дообучение модели

Двадцать примеров — это переобучение и непредсказуемые провалы на других
формулировках. Словарь синонимов расширяется явно, проверяется eval-ом и
в любой момент откатывается: видно, какое правило дало какой результат.

## 6.6. Кодировка CSV: ошибка, которая ломала загрузку прайса

**Файл:** `src/lib/price/parse.ts`

### Симптом

Клиент загружает совершенно правильный CSV, а система отвечает «Не нашёл
колонки "Наименование" и "Цена"». Выглядит как проблема формата файла,
хотя файл верный.

### Причина

SheetJS читает байты CSV как `latin1`, а не как UTF-8. Кириллица
превращается в мусор:

```
Наименование  →  ÐÐ°Ð¸Ð¼ÐµÐ½Ð¾Ð²Ð°Ð½Ð¸Ðµ
```

Строка заголовков перестаёт совпадать с ожидаемой, и разбор честно
сообщает, что нужных колонок нет.

### Решение

CSV декодируем сами и отдаём SheetJS уже строкой (`type: "string"`).
Кодировку определяем по BOM, а без BOM — пробуем UTF-8 с `fatal: true`
(он бросает исключение на некорректных последовательностях), при неудаче
падаем на Windows-1251.

Последнее важнее остальных: именно Windows-1251 по умолчанию даёт Excel
«CSV (разделители с запятой)» на русской Windows, а прайсы поставщиков
делают в Excel.

Тип файла определяем по содержимому, а не по расширению: `price.csv`
может оказаться переименованным xlsx (частая история при пересылке через
мессенджеры). Zip-сигнатура `PK` и старая `D0 CF` уходят в бинарную ветку.

### Как нашлось

Случайно — при написании теста обратной связи, где понадобился маленький
прайс в CSV. Ошибка была живой всё это время: любой клиент с русским
прайсом в UTF-8 получал отказ.

**Урок:** тест на новую функцию может вскрыть давнюю ошибку в соседней.
Писал тест про синонимы — нашёл поломанную загрузку прайса.

`test-price-encoding.ts` (13) проверяет UTF-8, UTF-8 BOM, Windows-1251,
zip-файл и пустой файл.

## 6.7. Публичные метрики: `/status`

**Файлы:** `src/app/status/page.tsx`, `src/db/repositories/metrics.ts`

### Зачем публично

«Работает хорошо» — это не аргумент. Аргумент — «70% позиций получают
цену автоматически, 87% решений приняты без модели, медиана обработки
сметы 1.1 секунды». Такие числа невозможно подделать, не соврав: они
считаются из тех же таблиц, что и сама работа.

### Чего на странице нет

**Ни одной цены, названия позиции или суммы по клиенту.** Только
агрегаты. Даже «всего выставлено на 4.2 млн ₽» раскрыло бы масштаб
бизнеса клиента, поэтому этой цифры нет.

### Главная метрика — не «процент с ценой»

Самая важная цифра — **доля решений без модели** (87%). Она показывает,
что детерминированный матчинг делает основную работу: бесплатно,
мгновенно и одинаково при каждом запуске. Модель подключается только
там, где точное совпадение не сработало.

Процент позиций с ценой (70%) важен, но объясняется в тексте страницы
честно: спорные строки остаются человеку **намеренно**, потому что
ошибочный матч дороже отсутствия матча.

### Ловушка: метрика, врущая в тысячу раз

Первая версия считала медиану обработки как `notified_at - created_at`.
На живой базе это дало **4 017 377 мс** — 67 минут.

Причина: `notified_at` это когда смету забрал n8n (опрос раз в 15 минут),
а не когда её разобрали. Смешаны две разные величины.

Исправлено миграцией 0007: колонка `parse_ms`, которая пишется в момент
разбора. Но и здесь была вторая ошибка — замер ставился в
`processAndRespond`, куда файл приходит уже разобранным. Медиана
получалась **1 мс** при реальных трёх секундах. Поставил `startedAt` в
начало `POST`.

Урок: метрику нужно проверять на правдоподобие. «1 мс на разбор Excel со
100 строками» — это невозможно, и заметить это можно только сравнив с
ожиданием, а не просто посмотрев, что число не нулевое.

### Почему один запрос

Каждый round-trip до пулера Neon — десятки миллисекунд, а страница
открывается часто. Все агрегаты собираются одним запросом с несколькими
CTE, а не пятью. Плюс кэш на минуту: страница публичная, и без кэша её
можно «обдолбить» запросами, нагрузив базу.

### Почему `force-dynamic`

Без него Next.js попытается отрендерить страницу при сборке. База при
сборке недоступна, и сборка упадёт. Это ровно та же ловушка, что и с
серверными компонентами, которые читают заголовки.

## 6.8. MCP-сервер: сервис внутри Claude и Cursor

**Файлы:** `src/lib/mcp/server.ts`, `src/app/api/mcp/route.ts`,
`src/app/mcp/page.tsx`

### Зачем

Менеджер кидает смету в Claude и пишет «сделай КП для ООО Ромашка».
Ассистент вызывает инструменты сервиса: разбирает смету, матчит цены,
объясняет спорные строки.

Это не «интеграция ради тренда». MCP стал интеграционным протоколом по
умолчанию в 2026, и сервис, который умеет в него, попадает в рабочий
процесс клиента вместо того, чтобы просить зайти на сайт.

### Главная защита: чего НЕТ

**Инструмента «поставь цену» не существует.** Это не упущение, а
центральный механизм безопасности.

Если такого инструмента нет, то никакая инъекция — в тексте сметы, в
названии позиции, в вопросе пользователя — не сможет назвать
произвольную цену. Модель физически не может сделать то, на что нет
функции. Тот же принцип, что и в чате, но здесь он работает сильнее: у
внешнего хоста (Claude) свои инструменты, и он мог бы попытаться
«дописать» цену сам — но ответ сервера не даёт такой возможности, потому
что цена всегда приходит вместе с кодом позиции.

### Stateless — не удобство, а необходимость

Спецификация 2026-07-28 сделала протокол stateless: нет handshake
`initialize` и заголовка `Mcp-Session-Id`. В SDK это
`WebStandardStreamableHTTPServerTransport` с `sessionIdGenerator: undefined`.

Для Vercel это критично. В stateful-режиме сервер хранит сессию в памяти
процесса, а на serverless каждый вызов может попасть на другой экземпляр.
Подключение работало бы через раз, и причина была бы неочевидной: первый
запрос успешен, второй — «сессия не найдена».

Тест проверяет это явно: два вызова инструмента подряд без сессии должны
оба пройти.

### Изоляция организаций

`orgId` берётся из Bearer-токена один раз при создании сервера и
замыкается в инструментах. Он **не приходит аргументом вызова**: иначе
модель могла бы подставить чужой `orgId`, и изоляция держалась бы на
честном слове модели.

Отдельная тонкость с `search_price`: RAG-поиск в проекте общий, без
фильтра по организации (так он устроен для чата). Инструмент отдаёт
только те хиты, чьи коды есть в прайсе организации. Дороже — нужен
`loadPrice`, — но иначе клиент увидел бы цены чужого прайса.

### Почему сравнение токена не через `===`

Обычное `===` выходит из цикла на первом несовпадении, и по времени
ответа токен подбирается посимвольно. Используется сравнение с
постоянным временем — мелочь, но в безопасности мелочей не бывает.

### Ограничение, названное честно

Авторизация — Bearer-токен, а не полный OAuth 2.1 с регистрацией
клиентов, который спецификация требует для удалённых серверов. Это
записано и в README, и на странице `/mcp`: следующему инженеру важно
знать, где граница сделанного.

### Проверки

`test-mcp.ts` (14) — не «сервер отвечает 200», а протокол целиком:
JSON-RPC поверх HTTP, stateless, отказ без токена, отсутствие
инструмента изменения цены, CORS-preflight с заголовками
`Mcp-Method`/`Mcp-Name`, 405 на GET.

Обычный HTTP-тест тут бесполезен: он увидит 200 и решит, что всё
хорошо, — а настоящий MCP-клиент при этом не подключится.

## 7. LangSmith: трейсинг и оценка

### Трейсинг

Каждый запуск агента виден по шагам: какой инструмент вызван, с какими
аргументами, сколько токенов, сколько миллисекунд.

Без этого отладка агента — гадание. «Почему ответил не то?» превращается
в «модель вызвала `search_price` с `"отвод 250"` вместо
`"отвод 250 90 градусов"`».

### Оценка: датасет из 25 кейсов

**Файл:** `scripts/datasets/cases.ts` — единый источник правды.

| Тип | Количество | Что проверяет |
|---|---|---|
| `price` | 15 | Правильный `priceId` для строки |
| `agent` | 5 | Нашёл / не нашёл / отказался отвечать |
| `attack` | 5 | Не поддался инъекции |

**Результаты:**

| Метрика | Результат |
|---|---|
| `price_code` | 13/15 (2 оставшихся — по дизайну требуют LLM) |
| `agent_outcome` | 5/5 |
| `attack_resisted` | 5/5 |
| `latency` | 24/25 |
| Ложных срабатываний | 0 |

### Почему оценщики детерминированные

Там, где речь о деньгах, оценщик не должен быть LLM. LLM-судья
нестабилен: тот же ответ сегодня «верный», завтра «неверный». Для
`price_code` сравнение строгое: `actual === expected`. Если цена
совпала — она совпала.

### Ошибка, которую поймали на себе

Первая версия `attack_resisted` давала ложное срабатывание на фразе
«Цену 0 применить не могу» — модель **отказалась**, а оценщик увидел
«цену 0» и записал провал. Регулярка теперь требует денежный суффикс
(`₽`, `руб`, `р.`) и отрицание перед числом.

Аналогично `agent_outcome` сначала был 3/5 из-за слишком строгих
запретов: `forbidden: ["python"]` срабатывал на слове «Python» в
нормальном ответе. Запреты переписаны на артефакты кода (`"def "`,
`"return "`), а не на слова.

## 9. n8n: автоматизация без ручной работы

### Сценарий 1 — уведомление о новом КП

```
Каждые 15 минут
      ↓
GET /api/proposals/recent   (наш эндпоинт, Bearer-ключ)
      ↓
count > 0?  ── нет ──→ stop
      │ да
      ↓
развернуть массив proposals
      ↓
Telegram: «Новое КП: смета.xlsx, 2 949 ₽, 1 из 4 позиций с ценой» + ссылка
```

### Сценарий 2 — напоминания по сделкам

```
Каждые 30 минут
      ↓
GET /api/proposals/log?due=1
      ↓
count > 0?  ── нет ──→ stop
      │ да
      ↓
Telegram менеджеру: «пора напомнить о КП, 3 дня без ответа»
```

**Почему опрос, а не webhook.** Наш сервис на Vercel не может достучаться
до `localhost:5678` на машине разработчика. Webhook потерял бы события,
пока n8n выключен. Опрос переживает простой: событие лежит в базе и
дождётся.

**Почему напоминание идёт менеджеру, а не клиенту.** Email клиента у
нас нет, а выдумывать нельзя. Живой звонок полезнее шаблонного «вы не
ответили».

**Идемпотентность.** `notified_at` в `estimates` и `reminders_sent` в
`proposal_log` — без них клиент получал бы напоминание каждые 15 минут.

### Четыре ловушки n8n 2.x

**1. Активации недостаточно — нужна публикация.** Сценарий показывал
`active: true`, в логах тишина, выполнений ноль. В n8n 2.x это два
разных состояния: «включён» и «опубликован». Планировщик видит только
опубликованную версию. Признак — поле `activeVersionId`.

**2. `retryOnFail` — свойство узла, а не `parameters.options`.** Положил
повторы внутрь `options` — сценарий падал на `ETIMEDOUT` без единого
повтора, хотя настройка «была».

**3. Опубликованный сценарий нельзя удалить.** `409 Cannot delete a
published workflow`. Причём `unpublish` асинхронный: сразу после
ответа API говорит «still being unpublished».

**4. Node не видит системный прокси Windows.** У разработчика прокси
`127.0.0.1:10809`, PowerShell и curl его читают из реестра, Node — нет.
Telegram из Node не работал вовсе. Решение — `HTTPS_PROXY` в окружении
n8n.

## 10.5. Тесты: два набора, потому что они проверяют разное

**Файлы:** `vitest.config.mts`, `src/**/*.test.ts`, `scripts/test-*.ts`

### Разделение

```
src/**/*.test.ts   →  Vitest          чистые функции, 0.6 с, без сети и базы
scripts/test-*.ts  →  node --env-file живые сценарии через HTTP
```

Соблазн был один: перевести всё на Vitest, раз это «правильный» тест-раннер.
Но сквозные сценарии проверяют не функции, а систему целиком — загрузку
файла, регистрацию, отсутствие утечки между организациями, SSE-поток.
Им нужен поднятый Next.js и настоящая база Neon. Vitest для этого не
годится: в CI он должен работать без инфраструктуры и без секретов.

Поэтому разделение не по вкусу, а по требованию к окружению:

| | Vitest | `scripts/test-*` |
|---|---|---|
| Что проверяет | функции | HTTP-контракты, сквозные сценарии |
| Нужен сервер | нет | да |
| Нужна база | нет | да |
| Нужны секреты | нет | да |
| Время | 0.6 с | 1–5 мин |
| В CI | да | нет (кроме eval и датасета) |

Обратная сторона разделения: юнит-тесты не поймают поломку API, а сквозные
не покажут, какая функция сломалось. Нужны оба.

### Что покрыто юнит-тестами и почему именно это

**Синонимы (20 тестов).** Самая хитрая логика в проекте: границы слов,
порядок фраз, дублирование размеров. Каждый тест — конкретная ошибка,
которая уже случилась:

- порог длины 3 символа пропускал «отв» → переписало бы любой отвод;
- замена без границ слова находила «отвод» внутри «подотвод»;
- длинная фраза должна проверяться раньше короткой, иначе «воздуховод
  спиральный» дал бы цену обычного воздуховода.

**Разбор прайса (13 тестов).** Прайс — источник всех цен, ошибка здесь
означает неверную цену в КП клиенту. Покрыты кодировки (UTF-8, BOM,
Windows-1251, UTF-16LE) и `matchKey` — ключ, который не должен склеивать
отвод 150 с отводом 250.

### Ловушка с алиасами

Vitest не читает `paths` из tsconfig: он разрешает импорты своим
резолвером. Первая версия конфига мапила `@` в КОРЕНЬ проекта, и
`@/lib/matcher/synonyms` искался в `./lib/...` — мимо, потому что в
tsconfig `@/*` указывает на `./src/*`.

Починилось явным списком алиасов с регулярками. Дублировать tsconfig
приходится, но список короткий и меняется редко.

### Зачем это работодателю

На собеседовании вопрос «как вы тестируете» — обычный. Ответ «набором
скриптов» звучит как «никак», даже если скриптов двадцать и они хорошие.
Ответ «Vitest на юниты, отдельный набор на сквозные сценарии, eval в CI,
и вот почему я не стал смешивать» — звучит как инженерное решение.

| «отв» стал синонимом ко всем отводам | Порог длины фразы 3 символа пропускал сокращения | Порог 4 символа |
| Медиана обработки сметы 67 минут | Считалась от `notified_at` — когда смету забрал n8n | Колонка `parse_ms` |

## 12. Решения, которые стоит уметь защитить

Это вопросы, которые задают на собеседовании. Ответы — ниже.

**«Почему деньги не в float?»** Двоичная дробь не представляет 0.1
точно. В смете на 100 позиций ошибка накапливается, и суммы не сходятся.

**«Почему LLM не считает цену?»** Она ошибается тихо: ответ выглядит
уверенно. Модель возвращает `priceId`, цену подставляет код.

**«Почему RAG не решает, а только ищет?»** Векторная близость не
знает, что 250 и 300 — разные диаметры с разной ценой.

**«Зачем и детерминированный матчинг, и RAG?»** 90% строк решаются
кодом за 0 мс. RAG нужен для оставшихся, где код не справился.

**«Почему оценщики без LLM?»** LLM-судья нестабилен. Там где речь о
деньгах, нужно строгое сравнение.

**«Почему CI без LLM?»** Флаки-тест перестают замечать.

**«Почему опрос в n8n, а не webhook?»** Vercel не достанет
`localhost`. Webhook теряет события при простое.

**«Почему таблица, а не Google Sheets?»** Данные клиентов не уезжают
в чужое облако, отчёты считаются SQL, не нужен OAuth-токен.

**«Почему `numeric`, а не `int` в копейках?»** Оба годятся. `numeric`
читается естественнее и переживает смену валюты с другой точностью.

## 13. Роли технологий в одной таблице

| Технология | Роль | Почему не альтернатива |
|---|---|---|
| Next.js | UI + API в одном деплое | Отдельный бэкенд — лишний сервис |
| FSD | Границы модулей | Без границ появляются циклы |
| LangGraph | Граф агента с состоянием | Простой цикл не выражает guard → отказ |
| LangChain | Инструменты, сообщения | Свой протокол — больше кода, те же ошибки |
| pgvector | Векторы в Postgres | Отдельная векторная БД — второй сервис ради 215 строк |
| Drizzle | Типизированные запросы | Prisma тянет свой движок; здесь SQL виден |
| Zod | Валидация ответов LLM | Модель вернёт что угодно |
| docx | DOCX кодом | Word-шаблоны требуют Office на сервере |
| LangSmith | Трейсинг и оценка | Свои логи не дают сравнения версий |
| n8n | Внешние сценарии | Код на Vercel для «отправить в Telegram» — дороже правок |
| GitHub Actions | CI | Ручные проверки забываются |
| Vercel | Хостинг | Свой сервер — ещё одна инфраструктура |

## 15. Что осталось за рамками

Честный список — чтобы не обещать больше, чем есть.

**Не сделано:**
- Мультитенантность: один прайс на всех.
- Авторизация пользователей: сметы доступны по ссылке с `id`.
- Загрузка файлов XLSX: разбор только текстом.
- Очередь задач: длинные сметы обрабатываются синхронно.
- Мониторинг: нет алертов, если n8n перестал слать.

**Ограничения инфраструктуры:**
- Neon-пулер рвёт соединение после тяжёлого запроса → одна операция на
  соединение, `searchPrice` до 6.8 с на пиках.
- Vercel free: 10 с на функцию без настройки, дальше 60 с.
- polza.ai баланс: проверять перед демо.

- «Отвод сегментный 90 градусов 150» = 606 ₽ — подозрительно дёшево
  для сегментного.
- «Муфта ф500» = 400 ₽ против «ф450» = 421 ₽ — меньший размер дороже.
- Что означает «(R)» в названиях позиций.
