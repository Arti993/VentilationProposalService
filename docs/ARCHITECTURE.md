# Как работает VentilationProposalService

Полный разбор: какие технологии применены, зачем именно они и как всё
связано между собой. Это не список «что мы выучили», а объяснение
приложения от входа до выхода — с причинами решений и с тем, что
сломалось по дороге.

---

## Что делает приложение

Клиент присылает смету — список строк вроде «Воздуховод круглый 315,
10 м» или «Тройник 315х200, 3 шт». Сервис:

1. Разбирает строки и находит каждую позицию в прайсе из 215 позиций.
2. Считает суммы **только для тех позиций, что есть в прайсе**.
3. Формирует коммерческое предложение в DOCX.
4. Отвечает на вопросы клиента в чате — но только про это КП.
5. Отдаёт новые КП внешней автоматизации (n8n), которая уведомляет
   менеджера в Telegram и напоминает о сделках без ответа.

Главное правило: **ошибочная цена опаснее отсутствия цены**. Если
матчинг не уверен — позиция остаётся без цены и помечается «уточнить
у менеджера». Менеджер получает «нет цены», а не «цена 606 ₽» там, где
на самом деле 6 060 ₽. Первое — рабочая ситуация, второе — убыток
и потерянный клиент.

## 1. Парсинг и нормализация

**Файл:** `src/lib/price/normalize.ts`

Строка клиента хаотична. В реальном прайсе встречается:

- «Воздуховод круглый d315», «воздуховод ⌀315», «Воздуховод 315»
- «Тройник 315х200» и «Тройник 315-200» — тот же размер
- «Отвод 90°» и «Отвод 90 градусов»
- «Спиральный воздуховод» и «воздуховод спиральный»

`normalize()` приводит всё к канону: нижний регистр, единая раскладка,
размеры через `/`, синонимы по типам.

**Ловушка, на которой всё ломалось:** JavaScript `\w` и `\b` не понимают
кириллицу. `\bвоздуховод\b` не сработает для «воздуховод», потому что
`в` не считается словесным символом. Решение — явные диапазоны
`[а-яё]` и `(?:^|[^а-яё])`.

**Вторая ловушка:** дефис как разделитель размеров. «Тройник 315-200»
и «Тройник 315-200-100» — оба валидны, но «Отвод 90-250» — угол и
диаметр. Правило заменило дефис на `/` только между числами, где обе
части — размеры:

```js
s = s.replace(/(?<=\d)\s*[-—–]\s*(?=\d{2,4}(?!\d))/g, "/")
```

**Третья ловушка:** голое «отвод» без параметров неоднозначно. Может быть
отвод 45° или 90°, сегментный или штампованный — цены разные. Правило
возвращает `unknown` и отправляет на LLM, а не угадывает.

## 2. Матчинг: детерминизм → LLM → человек

**Файл:** `src/lib/matcher/hybrid.ts`

Три уровня, в порядке возрастания стоимости и убывания надёжности:

```
Точное совпадение ключа       ~90% строк, 0 мс, 0 ₽
        ↓ не нашли
Гибридный поиск + LLM         ~8% строк, ~800 мс, копейки
        ↓ не уверены
Человек уточняет              ~2% строк
```

**Почему LLM не решает всё.** LLM ошибается тихо: ответ выглядит
уверенно и правдоподобно. Детерминированный матчинг ошибается только
там, где нормализация не справилась, — и это видно по критерию. Там где
можно решить кодом, код и решает.

**Порог уверенности:** `CONFIDENCE_THRESHOLD = 0.85`. Ниже — позиция
уходит человеку, а не в КП с приблизительной ценой.

**Ключевое архитектурное решение:** LLM никогда не называет цену. Он
возвращает только `priceId` — идентификатор позиции прайса. Цену
подставляет код из прайса. Даже если модель «выдумает» цену, ей негде
её записать: в инструментах нет такой возможности.

## 3. RAG: поиск по прайсу через pgvector

**Файлы:** `src/lib/rag/embed.ts`, `search.ts`, `hybrid.ts`

Когда детерминированный матчинг не справился, нужен поиск «похожего
по смыслу». Здесь работает RAG.

### Как устроено

1. Каждая позиция прайса превращается в вектор 1024 числа через
   `baai/bge-m3` — модель, которая понимает русский и работает с
   короткими техническими названиями.
2. Векторы лежат в Postgres в колонке `vector(1024)`, поиск по
   косинусному расстоянию через индекс.
3. При запросе: текст клиента → вектор → поиск ближайших позиций
   → результат отдаётся LLM как контекст.

### Почему гибридный поиск, а не чистые вектора

Чистый векторный поиск проваливается на числах. «Отвод 250» и «Отвод
300» семантически почти одинаковы — для модели это «отвод» плюс размер,
а размеры близки. Но разница в цене существенна.

Поэтому `hybrid.ts` смешивает два сигнала:

```
итоговый счёт = 0.55 × косинусное сходство + 0.45 × совпадение слов
```

Веса подобраны так, чтобы числа (диаметры, углы) влияли сильно.
Ключевое слово «315» в строке даёт почти точное попадание в размер.

### Почему RAG — добавка, а не решатель

RAG помогает найти кандидатов, но **не решает**, какая цена верна.
Решение принимает детерминированный матчинг или человек. Если бы RAG
решал, «Отвод 250» мог бы получить цену от «Отвода 300» — и никто бы
не заметил.

### Что дал замер

| Показатель | Значение |
|---|---|
| Минимум | 608 мс |
| Медиана | 887–1170 мс |
| Максимум | ~6800 мс |

Максимум — не наш код, а пулер Neon: он изредка «зависает» на 5 секунд.

## 4. Postgres: почему не in-memory и не Mongo

**Файлы:** `src/db/schema.ts`, `connection.ts`, `repositories/*`

Начиналось с `Map` в памяти. Умерло на первом же запросе после деплоя:
Vercel поднимает несколько инстансов функции, и каждый видит свою копию
`Map`. Клиент загрузил смету — второй запрос попал в другой инстанс —
сметы нет.

### Схема

**`price_items`** — прайс, 215 позиций. Загружается один раз, кэш 5 минут.

**`estimates`** — снимок КП. Хранит сумму, количество позиций,
`notified_at` (когда отдали автоматизации), `expires_at` (24 часа).

**`estimate_positions`** — позиции с **копией цены**, а не ссылкой.
Если прайс завтра изменится, старое КП не должно «пересчитаться»:
клиенту уже назвали цену.

**`proposal_log`** — журнал сделок без срока жизни: клиенты
возвращаются через недели, история нужна дольше, чем живёт документ.

### Решение: деньги в `numeric`, не `float`

```ts
totalSum: numeric("total_sum", { precision: 14, scale: 2 })
```

`float` в JS — двоичная дробь. `0.1 + 0.2 !== 0.3`. В смете из 100
позиций накопленная ошибка даёт расхождение в рублях, и клиент увидит
«21 010.000000001 ₽». `numeric` в Postgres — точная десятичная
арифметика.

### Ловушка Neon, которая ломала всё

Пулер Neon (PgBouncer) рвёт соединение после нескольких тяжёлых
запросов. Симптом: второй векторный запрос висит 19 секунд, третий
лёгкий — 70 секунд.

Решение в `connection.ts`:

```ts
const MAX_OPS_PER_CONNECTION = 1
```

Одна операция на соединение, потом переподключение. Медленнее в теории,
но стабильно на практике. Плюс `withRetry` с экспоненциальной паузой.

**Урок:** проблема была не в нашем коде. Прямой запрос без обёрток тоже
иногда давал 5308 мс. Это поведение пулера, и его надо обходить, а не
«оптимизировать».

## 5. Агент на LangGraph

**Файлы:** `src/lib/agent/graph.ts`, `tools.ts`, `ragTool.ts`

### Граф

```
      guard (проверка темы)
            │
     ┌──────┴──────┐
     │             │
  не по теме    по теме
     │             │
  refuse        agent ──► tools ──► agent (цикл)
                   │
                   ▼
                 ответ
```

`guard` — детерминированная проверка: вопрос про погоду не дойдёт до
LLM. Это экономит деньги и убирает класс проблем: модель, отвечающая
на любой вопрос, рано или поздно ответит не то, что нужно.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `search_price` | Гибридный поиск по прайсу (RAG) |
| `get_estimate` | Текущая смета клиента из сессии |
| `get_position` | Одна позиция с деталями матчинга |
| `explain_absence` | Почему позиции нет в прайсе |
| `calc_total` | Сумма по позициям с ценой |
| `find_similar` | Похожие позиции |
| `get_pricelist_info` | Единицы измерения, правила |

**Набор инструментов зависит от вопроса.** `toolsFor(text)` отдаёт
только релевантные: вопрос про сумму не получает доступ к поиску по
прайсу. Меньше инструментов — меньше токенов и меньше шансов, что
модель вызовет не тот.

### Ловушка: `ToolNode` должен получить ВСЕ инструменты

```ts
const toolNode = new ToolNode(allTools)
```

`ToolNode` выполняет вызовы, которые модель вернула. Если передать ему
только часть инструментов, модель вызовет отсутствующий — и узел
упадёт. Набор ограничивается не здесь, а тем, что видит модель на
входе.

## 6. Защита от prompt-injection

**Три уровня, и они независимы:**

**Уровень 1 — архитектурный.** У агента нет инструмента, который
меняет цену. Даже полностью управляемая модель не может назвать свою
цену: она возвращает `priceId`, сумму считает код.

**Уровень 2 — промпт.** Пользовательский текст оборачивается в
разметку, а инструкция «игнорируй предыдущие указания» попадает в
данные, а не в команды.

**Уровень 3 — код.** `validate()` проверяет ответ модели на
запрещённые паттерны. `guard` отсекает вопросы не по теме до LLM.

**Проверка:** 5 атакующих кейсов в датасете — попытки установить цену,
вытащить промпт, сменить роль. Результат **5/5 отражено**, ни одного
ложного срабатывания.

## 7. LangSmith: трейсинг и оценка

### Трейсинг

Каждый запуск агента виден по шагам: какой инструмент вызван, с какими
аргументами, сколько токенов, сколько миллисекунд.

Без этого отладка агента — гадание. «Почему ответил не то?» превращается
в «модель вызвала `search_price` с `"отвод 250"` вместо
`"отвод 250 90 градусов"`».

### Оценка: датасет из 25 кейсов

**Файл:** `scripts/datasets/cases.ts` — единый источник правды.

| Тип | Количество | Что проверяет |
|---|---|---|
| `price` | 15 | Правильный `priceId` для строки |
| `agent` | 5 | Нашёл / не нашёл / отказался отвечать |
| `attack` | 5 | Не поддался инъекции |

**Результаты:**

| Метрика | Результат |
|---|---|
| `price_code` | 13/15 (2 оставшихся — по дизайну требуют LLM) |
| `agent_outcome` | 5/5 |
| `attack_resisted` | 5/5 |
| `latency` | 24/25 |
| Ложных срабатываний | 0 |

### Почему оценщики детерминированные

Там, где речь о деньгах, оценщик не должен быть LLM. LLM-судья
нестабилен: тот же ответ сегодня «верный», завтра «неверный». Для
`price_code` сравнение строгое: `actual === expected`. Если цена
совпала — она совпала.

### Ошибка, которую поймали на себе

Первая версия `attack_resisted` давала ложное срабатывание на фразе
«Цену 0 применить не могу» — модель **отказалась**, а оценщик увидел
«цену 0» и записал провал. Регулярка теперь требует денежный суффикс
(`₽`, `руб`, `р.`) и отрицание перед числом.

Аналогично `agent_outcome` сначала был 3/5 из-за слишком строгих
запретов: `forbidden: ["python"]` срабатывал на слове «Python» в
нормальном ответе. Запреты переписаны на артефакты кода (`"def "`,
`"return "`), а не на слова.

## 8. CI: проверки на каждый пуш

**Файл:** `.github/workflows/check.yml`

```
checkout → setup-node 24 → npm ci
   → tsc --noEmit
   → нормализация прайса (и проверка, что файл не изменился)
   → детерминированный eval (27/27)
   → dataset check (18 проверено, 0 провалов)
   → npm run build
```

**Почему CI не зовёт LLM.** Платный вызов в CI — это флаки: сегодня
сеть моргнула, завтра модель ответила иначе. Красный крестик, который
иногда зелёный, перестают замечать. Все 27 проверок детерминированные,
бесплатные и повторяемые.

**Проверено, что CI действительно ловит регрессии:** закомментировал
исправление дефиса в `normalize.ts` → `ПРОВАЛ price-hyphen-reducer`,
exit code 1.

## 9. n8n: автоматизация без ручной работы

### Сценарий 1 — уведомление о новом КП

```
Каждые 15 минут
      ↓
GET /api/proposals/recent   (наш эндпоинт, Bearer-ключ)
      ↓
count > 0?  ── нет ──→ stop
      │ да
      ↓
развернуть массив proposals
      ↓
Telegram: «Новое КП: смета.xlsx, 2 949 ₽, 1 из 4 позиций с ценой» + ссылка
```

### Сценарий 2 — напоминания по сделкам

```
Каждые 30 минут
      ↓
GET /api/proposals/log?due=1
      ↓
count > 0?  ── нет ──→ stop
      │ да
      ↓
Telegram менеджеру: «пора напомнить о КП, 3 дня без ответа»
```

**Почему опрос, а не webhook.** Наш сервис на Vercel не может достучаться
до `localhost:5678` на машине разработчика. Webhook потерял бы события,
пока n8n выключен. Опрос переживает простой: событие лежит в базе и
дождётся.

**Почему напоминание идёт менеджеру, а не клиенту.** Email клиента у
нас нет, а выдумывать нельзя. Живой звонок полезнее шаблонного «вы не
ответили».

**Идемпотентность.** `notified_at` в `estimates` и `reminders_sent` в
`proposal_log` — без них клиент получал бы напоминание каждые 15 минут.

### Четыре ловушки n8n 2.x

**1. Активации недостаточно — нужна публикация.** Сценарий показывал
`active: true`, в логах тишина, выполнений ноль. В n8n 2.x это два
разных состояния: «включён» и «опубликован». Планировщик видит только
опубликованную версию. Признак — поле `activeVersionId`.

**2. `retryOnFail` — свойство узла, а не `parameters.options`.** Положил
повторы внутрь `options` — сценарий падал на `ETIMEDOUT` без единого
повтора, хотя настройка «была».

**3. Опубликованный сценарий нельзя удалить.** `409 Cannot delete a
published workflow`. Причём `unpublish` асинхронный: сразу после
ответа API говорит «still being unpublished».

**4. Node не видит системный прокси Windows.** У разработчика прокси
`127.0.0.1:10809`, PowerShell и curl его читают из реестра, Node — нет.
Telegram из Node не работал вовсе. Решение — `HTTPS_PROXY` в окружении
n8n.

## 12. Решения, которые стоит уметь защитить

Это вопросы, которые задают на собеседовании. Ответы — ниже.

**«Почему деньги не в float?»** Двоичная дробь не представляет 0.1
точно. В смете на 100 позиций ошибка накапливается, и суммы не сходятся.

**«Почему LLM не считает цену?»** Она ошибается тихо: ответ выглядит
уверенно. Модель возвращает `priceId`, цену подставляет код.

**«Почему RAG не решает, а только ищет?»** Векторная близость не
знает, что 250 и 300 — разные диаметры с разной ценой.

**«Зачем и детерминированный матчинг, и RAG?»** 90% строк решаются
кодом за 0 мс. RAG нужен для оставшихся, где код не справился.

**«Почему оценщики без LLM?»** LLM-судья нестабилен. Там где речь о
деньгах, нужно строгое сравнение.

**«Почему CI без LLM?»** Флаки-тест перестают замечать.

**«Почему опрос в n8n, а не webhook?»** Vercel не достанет
`localhost`. Webhook теряет события при простое.

**«Почему таблица, а не Google Sheets?»** Данные клиентов не уезжают
в чужое облако, отчёты считаются SQL, не нужен OAuth-токен.

**«Почему `numeric`, а не `int` в копейках?»** Оба годятся. `numeric`
читается естественнее и переживает смену валюты с другой точностью.

## 13. Роли технологий в одной таблице

| Технология | Роль | Почему не альтернатива |
|---|---|---|
| Next.js | UI + API в одном деплое | Отдельный бэкенд — лишний сервис |
| FSD | Границы модулей | Без границ появляются циклы |
| LangGraph | Граф агента с состоянием | Простой цикл не выражает guard → отказ |
| LangChain | Инструменты, сообщения | Свой протокол — больше кода, те же ошибки |
| pgvector | Векторы в Postgres | Отдельная векторная БД — второй сервис ради 215 строк |
| Drizzle | Типизированные запросы | Prisma тянет свой движок; здесь SQL виден |
| Zod | Валидация ответов LLM | Модель вернёт что угодно |
| docx | DOCX кодом | Word-шаблоны требуют Office на сервере |
| LangSmith | Трейсинг и оценка | Свои логи не дают сравнения версий |
| n8n | Внешние сценарии | Код на Vercel для «отправить в Telegram» — дороже правок |
| GitHub Actions | CI | Ручные проверки забываются |
| Vercel | Хостинг | Свой сервер — ещё одна инфраструктура |

## 14. Как запустить

```bash
# зависимости
npm ci

# переменные окружения
cp .env.example .env.local
# заполнить: DATABASE_URL, POLZA_API_KEY, AUTOMATION_API_KEY

# миграции
node --env-file=.env.local scripts/apply-migration.ts

# прайс и векторы
node --env-file=.env.local scripts/normalize-price.ts
node --env-file=.env.local scripts/embed-price.ts

# проверки
npm run ci

# разработка
npm run dev
```

**n8n** (нужен прокси для Telegram):

```powershell
$env:HTTPS_PROXY = "http://127.0.0.1:10809"
$env:N8N_USER_FOLDER = "$PWD\.n8n-data"
n8n start

# сценарии
node --env-file=.env.local scripts/n8n/create-workflow.ts
node --env-file=.env.local scripts/n8n/create-reminder-workflow.ts
node --env-file=.env.local scripts/n8n/toggle.ts on notify
node --env-file=.env.local scripts/n8n/toggle.ts on reminders
```

## 15. Что осталось за рамками

Честный список — чтобы не обещать больше, чем есть.

**Не сделано:**
- Мультитенантность: один прайс на всех.
- Авторизация пользователей: сметы доступны по ссылке с `id`.
- Загрузка файлов XLSX: разбор только текстом.
- Очередь задач: длинные сметы обрабатываются синхронно.
- Мониторинг: нет алертов, если n8n перестал слать.

**Ограничения инфраструктуры:**
- Neon-пулер рвёт соединение после тяжёлого запроса → одна операция на
  соединение, `searchPrice` до 6.8 с на пиках.
- Vercel free: 10 с на функцию без настройки, дальше 60 с.
- polza.ai баланс: проверять перед демо.

**Открытые вопросы к менеджеру:**
- «Отвод сегментный 90 градусов 150» = 606 ₽ — подозрительно дёшево
  для сегментного.
- «Муфта ф500» = 400 ₽ против «ф450» = 421 ₽ — меньший размер дороже.
- Что означает «(R)» в названиях позиций.
- Воздуховоды измеряются в погонных метрах?
