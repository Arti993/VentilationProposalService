# n8n: что смотреть и где

Справочник по мониторингу автоматизаций проекта «Воздуховод».
Записан после того, как на грабли наступили вживую.

## Что n8n видит, а что нет

n8n стоит в **конце** процесса. Он не участвует в загрузке сметы, парсинге,
матчинге и чате — он забирает уже готовое КП из базы и отправляет менеджеру.

| Вопрос | n8n ответит? |
|---|---|
| Сколько смет загрузили | ❌ нет — это до n8n |
| Доля позиций с ценой | ❌ нет |
| Что спрашивают в чате | ❌ нет |
| Сколько ушло уведомлений | ✅ да |
| Дошло ли до Telegram | ✅ да |
| Кому пора напомнить | ✅ да |
| Падал ли сценарий | ✅ да |

Для бизнес-аналитики используйте SQL по Postgres (`scripts/analytics-audit.ts`).
n8n — только про доставку.

## Где смотреть

### 1. Интерфейс (для разового разбора)

```
http://localhost:5678
```

**Overview → Executions** — список запусков с фильтром по сценарию и статусу.
Клик на запуск → данные на каждом узле: что вернул HTTP, что ушло в Telegram.

### 2. Отчёт одной командой (для общей картины)

```bash
node --env-file=.env.local scripts/n8n/report.ts
node --env-file=.env.local scripts/n8n/report.ts --limit 100
node --env-file=.env.local scripts/n8n/report.ts --json
```

Показывает: сколько запусков, **сколько полезных**, интервал, падения с текстом.

### 3. API (для своих отчётов)

```bash
GET /api/v1/executions?workflowId=<id>&limit=50
GET /api/v1/executions/<id>?includeData=true
Header: X-N8N-API-KEY
```

## Главная ловушка: запуски ≠ работа

Планировщик будит сценарий каждые 15 минут. Но в большинстве запусков
новых КП нет, и он ничего не отправляет.

```
16 запусков  →  5 действий
```

Если смотреть на список вида «16 запусков», легко решить, что ушло
16 уведомлений. Отчёт специально различает эти числа: смотрит, сколько
элементов прошло через узел отправки.

**Плата за опрос:** 3 запуска на одно действие. Это нормально — цена за то,
что событие не теряется, если n8n лежал.

## Сторож ошибок

Сценарий **«КП: сторож ошибок»** присылает в Telegram сообщение при падении
любого сценария проекта.

```
🚨 Автоматизация сломалась

Сценарий: КП: уведомление о новом предложении
Узел: Уведомить в Telegram
Выполнение: #3

Ошибка:
The connection timed out...
```

### Как он устроен

```
Error Trigger → Фильтр «не о себе» → Telegram
```

### Ловушка 1: Error Trigger сам по себе молчит

Узел `n8n-nodes-base.errorTrigger` **не видит ошибок**, пока сценарию не
прописан `settings.errorWorkflow`. Это отсылка «если упаду — сообщи туда».
Без неё сторож висит активным, выглядит работающим и не видит ничего.

Глобальной настройки «все ошибки шлём в X» в публичном API self-hosted n8n нет.

```ts
// каждому сценарию, за которым следим
settings: { errorWorkflow: "<id сторожа>" }
```

Скрипт `test-error-watchdog.ts` проставляет привязку всем сценариям разом.

### Ловушка 2: `$env` в выражениях запрещён

n8n 2.x по умолчанию не даёт выражениям читать переменные окружения.

```ts
// ❌ падает с «access to env vars denied»
url: "=https://api.telegram.org/bot{{ $env.TELEGRAM_BOT_TOKEN }}/sendMessage"
```

Правильно — credentials: токен живёт в зашифрованном хранилище n8n,
в текст сценария не попадает.

```ts
credentials: { telegramApi: { id: "<id>", name: "Telegram · сторож ошибок" } }
```

**Почему не включил `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`:** тогда секрет
доступен из любого узла любого сценария, включая тот, куда однажды
скопируют чужой код из интернета. Лишний риск без выгоды.

### Ловушка 3: сторож должен молчать о себе

Фильтр «не о себе» обязателен. Без него падение сторожа породит сообщение
о падении сторожа, которое упадёт снова — и так по кругу.

### Проверка

```bash
node --env-file=.env.local scripts/n8n/create-error-workflow.ts  # создать
node --env-file=.env.local scripts/n8n/test-error-watchdog.ts    # проверить
```

Второй скрипт роняет временный сценарий, ждёт реакции, удаляет за собой.
Проверка «урони и посмотри» обязательна: сторож молчит и когда всё хорошо,
и когда он сломан. Отличить одно от другого можно только аварией.

## Ловушка 4: Кириллица в PowerShell

`Invoke-RestMethod` с JSON-телом **портит кириллицу**. Название сценария
однажды превратилось в `??: ??????????? ? ????? ???????????` — и осталось
бы таким, если не проверить.

Причина: PowerShell сериализует JSON в cp1251, а n8n ждёт UTF-8.

Правило: **изменять сценарии только через node `fetch`**, не через
`Invoke-RestMethod` с телом.

```js
await fetch(url, {
  method: 'PUT',
  headers: { 'X-N8N-API-KEY': key, 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Кириллица' }),   // node отправляет UTF-8
});
```

Если файл уже испорчен — пересоздать имя тем же способом.

## Ограничения

**История удаляется сама.** По умолчанию n8n чистит выполнения старше
14 дней или сверх 10 000 записей.

**Ручной запуск через API недоступен.** `POST /workflows/{id}/run` отвечает
`405` — такого метода нет в публичном API. Только расписание или кнопка
в интерфейсе.

**Данные локальные.** n8n на компьютере, приложение на Vercel. Выключили
компьютер — уведомления не уходят, в истории дыра. Событие ждёт в базе
(поэтому опрос, а не webhook), но разгребать их сценарий начнёт, только
когда проснётся.

## Прунинг: если история нужна дольше

```env
EXECUTIONS_DATA_PRUNE=true
EXECUTIONS_DATA_MAX_AGE=336        # 14 дней
EXECUTIONS_DATA_SAVE_ON_SUCCESS=all
```

Для учебного проекта хватает значений по умолчанию.
