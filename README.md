# VentilationProposalService

[![Проверка](https://github.com/Arti993/VentilationProposalService/actions/workflows/check.yml/badge.svg)](https://github.com/Arti993/VentilationProposalService/actions/workflows/check.yml)

Сервис автоматической подготовки коммерческих предложений (КП) по сметам клиентов
для вентиляционного оборудования.

## Задача

Клиент присылает смету — список позиций (воздуховоды, тройники, переходы, отводы).
Сервис сопоставляет каждую позицию с прайс-листом и формирует КП:

- позиции **есть** в прайсе → подставляется цена;
- позиций **нет** → строка остаётся без цены, с пометкой «нет в прайсе»;
- спорные случаи → помечаются для ручной проверки, а не угадываются.

## Принцип: ошибочный матч опаснее отсутствия матча

Цена в КП — это деньги компании. Поэтому:

- цена ставится **только** при однозначном совпадении типа и размеров;
- при нескольких вариантах исполнения — статус `ambiguous`, цена не ставится;
- если строку не удалось разобрать — статус `needs_llm`, без цены.

LLM используется **только** для разбора сложных формулировок, но никогда
не придумывает цены — цены берутся исключительно из БД.

## RAG по прайсу (pgvector)

Поиск позиции, когда клиент называет её своими словами: «воздух спиральный
315», «отвод девяносто на двести пятьдесят», «переход 400-315».

```bash
node scripts/index-price.ts    # проиндексировать прайс (215 позиций, ~20 мин)
node scripts/index-status.ts   # сколько проиндексировано
node scripts/test-search.ts    # чистый векторный поиск
node scripts/test-hybrid.ts    # гибрид с предохранителями
node scripts/bench-rag.ts      # RAG против детерминированного матчера
node scripts/test-rag-agent.ts # агент пользуется search_price
```

### Как устроено

1. **Эмбеддинги** — `baai/bge-m3`, 1024 измерения, вектор нормализован.
2. **Хранение** — колонка `embedding vector(1024)` в `price_items`,
   HNSW-индекс с `vector_cosine_ops`.
3. **Поиск** — косинусное расстояние `<=>` в Postgres.
4. **Переранжирование** — гибрид: 0.55 × вектор + 0.45 × доля найденных
   ключевых слов. Нужно потому, что вектор смотрит на весь текст и в
   «хомут для воздуховода 315» цепляется за «воздуховод».
5. **Предохранители** — три независимые проверки, каждая может отсечь
   выдачу целиком (см. ниже).
6. **Инструмент агента** — `search_price`. Агент зовёт его, когда человек
   спрашивает про наличие и цену словами, а не про загруженную смету.

### Главный принцип: ошибочная цена опаснее отсутствия

RAG умеет находить «похожее», а для сметы это опасно: на запрос про хомут
он уверенно вернёт воздуховод 315, потому что размер совпал. Поэтому выдача
RAG проходит через три предохранителя, и любой из них может её обнулить:

| Предохранитель | Что ловит | Пример |
|---|---|---|
| Товар не из прайса | крепёж, гибкие вставки, автоматика | «хомут 315» → пусто |
| Тип изделия | несовпадение типа | «вставка» ≠ «врезка» → пусто |
| Размеры | размера нет ни у одного кандидата | «воздуховод 999» → пусто |

Плюс числа словами заменяются на цифры **до** эмбеддинга: без этого
«тройник триста пятнадцать на двести» давал одинаковое сходство ~0.52 у
всех тройников, и нужный не попадал даже в топ-10.

### Результат бенчмарка

15 строк сметы: 9 существующих позиций, 3 написанных «как клиент», 3 таких,
которых в прайсе нет.

| Режим | Верно | **Ложно** | Не найдено |
|---|---|---|---|
| Детерминированный матчер | 10/15 | 0 | 5 |
| RAG + предохранители | **15/15** | **0** | 0 |
| Каскад: матчер → RAG | **15/15** | **0** | 0 |

RAG выигрывает там, где матчер пасует: разговорные названия, опечатки,
дефисы вместо дробей, числа словами. И не добавляет ни одного ложного
совпадения — это и было главным требованием.

### Ограничения инфраструктуры

Пуллер Neon накладывает жёсткие лимиты, и они определили реализацию:

- вектор округляется до **2 знаков** (5.1 КБ вместо 11.8 КБ) — при 4 знаках
  запрос висит 5.5 с вместо 0.6 с;
- в SQL вектор передаётся **один раз** через CTE: два вхождения литерала
  удваивают объём и рвут соединение;
- соединение выдерживает **2 запроса**, третий висит ~70 с и падает — это
  выяснилось постраничным чтением прайса, где рвалась каждая третья
  страница;
- выдача шире **10 строк** не проходит, поэтому `pool = 10`;
- эмбеддинги кэшируются в памяти процесса: повтор того же вопроса
  экономит ~1.5 с.

### Токены: 97% промпта — это описания инструментов

Замер по трассам LangSmith показал неожиданное:

| Часть | Токены | Доля |
|---|---|---|
| prompt | 16 138 | **97%** |
| completion | 483 | 3% |

То есть модель почти не рассуждает — почти всё время и деньги уходят на
отправку контекста. Внутри промпта картина такая (замерено запросами с
разным набором инструментов):

| Что | Токены |
|---|---|
| системный промпт | 861 |
| сообщения диалога | 135 |
| **7 инструментов** | **1517** |

Инструменты — главная статья. Поэтому набор инструментов выбирается под
вопрос теми же регулярками, что и страж, без отдельного вызова LLM:

| Вопрос | Инструменты | Токенов было → стало |
|---|---|---|
| про товар/цену | прайс + RAG | 2798 → 1825 |
| про смету | сметные + RAG | 2798 → 2061 |

Ограничение: `ToolNode` получает **все** инструменты, а модель — только
выбранные. Иначе вызванный по имени инструмент не найдётся в узле.

### Проверка на каждый пуш (CI)

Workflow [.github/workflows/check.yml](.github/workflows/check.yml) запускается
на каждый пуш в `main` и на пул-реквест. Пять шагов, от дешёвых к дорогим:

| Шаг | Что проверяет |
|---|---|
| `tsc --noEmit` | типы |
| `normalize-price.ts` | все 215 строк прайса разбираются; файл не должен измениться |
| `eval.ts` | 27 эталонных строк смет с точными ценами |
| `datasets/check.ts` | 18 кейсов датасета, решаемых без LLM |
| `npm run build` | сборка Next.js |

Тот же набор локально: `npm run ci`.

Шаг нормализации сравнивает `data/price.normalized.json` с репозиторием и
**падает, если файл изменился**. Это не придирка: если правка в разборе
меняет нормализацию прайса, а результат не закоммичен, локально всё
работает, а на сервере цены считаются по старому файлу.

#### Чего в CI нет намеренно

**Вызовов LLM.** Они стоят денег и дают разный ответ от прогона к прогону.
Красный крест на таком кейсе означал бы «модель сегодня ответила иначе», а
не «код сломан» — то есть проверка перестала бы быть проверкой. Ответы
агента смотрят отдельно, прогоном `scripts/datasets/evaluate.ts` в LangSmith.

**Подключения к базе.** Прайс берётся из `data/price.normalized.json`.
Проверка не должна падать оттого, что Neon недоступен.

**Секретов.** Workflow проходит на форке без доступа к ключам.

#### Кейсы, которым нужна модель

Два кейса — «Отвод 90 градусов 250» и «отвод 90 на 250» — помечены
`needsLlm: true`. Детерминированный матчер **правильно** их не решает: вид
отвода не указан (сегментный или штампованный), а угадывать цену нельзя.
Без пометки CI считал бы корректный отказ поломкой и всегда был бы красным.

### Оценка качества в LangSmith

Датасет `kp-service-eval` — 25 кейсов в трёх группах:

| Группа | Кейсов | Что проверяет |
|---|---|---|
| `price` | 15 | находит ли система правильный код позиции |
| `agent` | 5 | отвечает ли агент по делу и не выдумывает ли цены |
| `attack` | 5 | отражает ли защита подмену цены и увод в сторону |

```
node --env-file=.env.local scripts/datasets/upload.ts      # залить кейсы
node --env-file=.env.local scripts/datasets/evaluate.ts all # прогнать и отправить
node --env-file=.env.local scripts/datasets/verify-eval.ts  # проверить в LangSmith
```

Перед запуском нужно задать `LANGSMITH_TRACING=true`: без него LangSmith SDK
не отправит результаты.

Кейсы живут в [scripts/datasets/cases.ts](scripts/datasets/cases.ts) —
раньше они были разбросаны по пяти скриптам, и что попадало в проверку,
решалось тем, какой скрипт вспомнили запустить.

#### Оценщики — детерминированные, не LLM-судья

| Оценщик | Что делает |
|---|---|
| `price_code` | точное сравнение кода позиции; отдельно помечает **ложное срабатывание** (выдали цену тому, чего нет в прайсе) |
| `agent_outcome` | подстроки: что обязано быть (`mustMention`) и чего быть не должно (`forbidden`) |
| `attack_resisted` | не применилась ли навязанная цена, не утёк ли промпт, не сменилась ли роль |
| `latency` | 1.0 до 6 с, 0.5 до 10 с, 0.0 после — регрессия по скорости видна сразу |

LLM-судью здесь использовать вредно: он «прощает» ошибку, которая стоит
денег клиенту.

#### Результат первого полного прогона

| Оценка | Результат |
|---|---|
| `price_code` | 13/15 |
| `agent_outcome` | 5/5 |
| `attack_resisted` | 5/5 |
| `latency` | 24/25 |
| **Ложных срабатываний** | **0** |

Два провала в `price` — «отвод 90 на 250» без указания вида (сегментный
или штампованный). Это **не баг**: вид не указан, а угадывать цену
нельзя. Такие строки по замыслу уходят к LLM.

#### Что датасет нашёл в первые же минуты

Три настоящие дыры, которых не видели прежние тесты:

1. **`переход 400-315` терял второй размер** — дефис не считался
   разделителем, `dims=[400]` вместо `[400,315]`, позиция не находилась.
2. **`воздух спиральный` не распознавался** — синоним был только для
   «воздуховод», без сокращения.
3. **`тройник триста пятнадцать на двести`** — числа словами матчер не
   понимал вовсе. Конвертация `digitsFromWords` была только в RAG-пути.

Все три исправлены; после этого `price_code` вырос с 10/15 до 13/15.

#### Оценщик может ошибаться чаще, чем система

Первые прогоны показали «провалы», которых не было:

- агент отвечал «Цену 0 применить не могу» — правильный отказ, но
  оценщик искал голый ноль в тексте и ругался;
- агент отвечал «в прайсе **нет**» — правильный ответ, но оценщик ждал
  точную фразу «нет в прайсе».

Поэтому проверки формулируются через деньги (`0 ₽`, `0 руб`) и наборы
корней, а не через точные фразы. Ложный провал в оценке хуже пропуска:
он заставляет «чинить» то, что работает.

### Скорость ответа агента

Первая версия отвечала за 12–23 секунды. Разбор по этапам показал, что
дело было не в LLM:

| Проблема | Было | Стало |
|---|---|---|
| Обрыв соединения на каждой 3-й странице прайса | 41 с на загрузку | 16 с |
| Прайс грузился всегда, даже когда не нужен | +16 с на вопрос | 0 |
| Агент звал 2–4 инструмента вместо одного | 23 с | 3–5 с |
| Финальный ответ | 12–23 с | **3–5 с** |

Что сделано:

1. **`MAX_OPS_PER_CONNECTION = 2`** — по замеру, третий запрос в соединении
   виснет на 70 секунд. Было 4, и половина страниц рвалась.
2. **Таймаут запроса 3 с** вместо 8: мёртвое соединение всё равно не
   ответит, лучше быстрее повторить на новом.
3. **Ленивая загрузка прайса** — `ToolContext.getPrice` стал функцией.
   Вопросы обслуживаются через `search_price` (поиск в базе), и прайс в
   памяти им не нужен вовсе.
4. **Правило «один вопрос — один инструмент»** в системном промпте:
   лишний вызов стоит ~1.5 с.
5. **Похожесть убрана из ответа инструмента** — модель цеплялась за число
   0.73 и добавляла «уточните» к верному ответу.



## Экспорт КП в DOCX

```bash
node scripts/test-docx.ts      # собрать документ и проверить содержимое
node scripts/test-download.ts  # проверить кнопку и скачивание в браузере
```

Кнопка «Скачать КП» на странице → `GET /api/proposal/[id]` → документ Word.

### Что попадает в документ

| В КП | Не в КП |
|---|---|
| Позиции с ценой | Статусы матчера |
| Названия из прайса | Причины решения от LLM |
| Цена, количество, сумма | Уверенность модели |
| Итог по позициям с ценой | Источник решения (LLM или правила) |
| Уточняемые позиции — списком, без цен | Строки, отброшенные как посторонние |

### Решения по документу

**Клиент не должен видеть внутреннюю кухню.** В КП уходят только позиции
с ценой; остальные — отдельным блоком «Позиции, требующие уточнения», без
цен и без объяснений. Статусы `not_found`, `needs_human`, уверенность
модели — это для менеджера, а не для клиента.

**Название берётся из прайса, а не из сметы клиента.** Клиент мог написать
«отвод 90 на 315» — в документе будет «Отвод сегментный 90 градусов 315»,
потому что именно это он получит.

**Сессия читается из БД по id.** Клиент не может подставить свои позиции
или цены в запрос на формирование документа.

**Проверка на пустоту.** Если ни одна позиция не получила цену, документ
не формируется — возвращается 422 с объяснением. Пустое КП хуже понятной
ошибки.

### Как проверялось

`test-docx.ts` распаковывает DOCX и проверяет не «файл создался», а
содержимое: нужные позиции на месте, а внутренние статусы и причины **не
утекли** в документ. Отдельно сверяется арифметика: сумма построчных
произведений совпадает с итогом (123 170 ₽ на офисной смете).

Визуально: документ отрендерен в PNG через LibreOffice Kit. Поля
соблюдены (126px слева при ожидаемых 124, 103px справа при 102), контент
занимает 79% страницы без обрезки, шрифты без подмен.

## База данных: Neon Postgres + Drizzle

```bash
npm run db:migrate    # применить миграции
npm run db:seed       # залить прайс (215 позиций)
npm run db:status     # состояние БД: таблицы, счётчики, пробный запрос
```

### Зачем Postgres

Сессии смет раньше жили в `Map` в памяти процесса. Это ломалось в двух
местах: холодный старт Vercel и переключение запроса на другой инстанс —
пользователь получал «смета не найдена» при живой смете. Теперь сессии в
Postgres и переживают и перезапуск, и деплой.

### Схема

| Таблица | Назначение |
|---|---|
| `price_items` | прайс-лист: код, название, цена, тип, размеры |
| `estimates` | загруженная смета: агрегаты, срок жизни |
| `estimate_positions` | позиции сметы: статус, цена, причина решения |

### Решения по схеме

**Деньги в `numeric(12,2)`, не `float`.** `0.1 + 0.2` в float даёт
`0.30000000000000004`. На 215 позициях прайса и смете на 40 строк
погрешность накопится до рубля — КП не сойдётся.

**Цены в КП — снимок, а не ссылка на прайс.** Если завтра цена изменится,
старое КП не должно пересчитаться само: клиенту уже назвали цифру.

**Позиции в отдельной таблице, не в JSON-колонке.** Нужны запросы вроде
«покажи все позиции со статусом not_found» — по JSON это seq scan.

**Миграции в репозитории.** SQL-файлы в `drizzle/` ревьюятся как код.

### Особенность Neon, которая ломала всё

При подключении через пулер Neon обнаружены два жёстких ограничения
(замерены скриптами `scripts/diag-*.ts`):

1. **Соединение выдерживает 4–5 запросов**, затем пулер его закрывает
   с `CONNECTION_CLOSED`.
2. **Один запрос больше ~11 КБ кириллицы** тоже рвёт соединение.
   Латиница того же объёма проходит — дело в байтах UTF-8.

Симптом выглядел как «баг драйвера»: простой `select` работает, вставка
215 позиций падает. Первые гипотезы (типы колонок, размер транзакции,
`channel_binding`) оказались неверными — проблема в лимитах пулера.

Решение — в `src/db/connection.ts`:

- **каждый запрос со своим соединением** (`withRetry`), а не общий пул;
- **автоматический повтор** при обрыве (3 попытки, растущая задержка);
- **нарезка по байтам, а не по строкам**: батч собирается динамически,
  пока размер SQL не достигнет 6 КБ;
- **чтение прайса постранично** по 60 строк — ответ на 215 строк не проходит.

Компромисс: заливка прайса не в одной транзакции. Если упадёт на середине,
останется часть данных — поэтому скрипт проверяет итоговое количество и
падает с ошибкой. Неполный прайс не должен выглядеть как успешный.

## UI: Next.js + FSD

```bash
npm run dev          # http://localhost:3000
npm run typecheck    # проверка типов
```

Интерфейс: загрузка сметы (drag&drop или кнопка демо), карточки-метрики,
таблица позиций с фильтрами и экспортом CSV, чат с агентом справа.
Клик по позиции в таблице — агент объясняет её статус.

### Структура FSD

```
src/
├── app/                  # Next.js App Router: только роутинг
│   ├── page.tsx          #   связывает роут с views
│   └── api/              #   API-роуты (вне FSD: серверный код)
├── views/                # композиция страниц
│   └── proposal/         #   страница КП
├── widgets/              # самостоятельные блоки
│   ├── estimate-summary/ #   карточки-метрики
│   └── estimate-table/   #   таблица позиций
├── features/             # действия пользователя
│   ├── upload-estimate/  #   загрузка сметы
│   └── send-chat-message/#   чат с агентом
├── entities/             # доменные сущности
│   └── estimate/         #   типы, статусы, бейдж
├── shared/               # переиспользуемое без домена
│   ├── api/              #   клиент к API
│   └── lib/              #   cn(), форматирование
└── lib/                  # серверная логика (матчер, LLM, агент)
```

**Почему `views`, а не `pages`.** В FSD слой называется `pages`, но в
Next.js App Router каталог `src/pages/` перехватывается Pages Router, и
сборка ломается на типах. Сообщество FSD для Next.js использует `views`.
Это не отход от методологии, а обязательная адаптация под фреймворк.

**Правила импортов соблюдены:** слой может импортировать только слои ниже
себя. `features` не знают о `widgets`, `entities` не знают о `features`,
`shared` не знает ни о ком.

### Решения по UI

**Типы — один источник правды.** `entities/estimate/model/types.ts`
используется и сервером, и клиентом. Дублирование контрактов между бэком
и фронтом — классический источник багов; здесь этого не случится.

**Сессия сметы на сервере.** Браузер передаёт только `sessionId`, данные
берутся из серверного хранилища. Если бы клиент присылал смету в теле
запроса, он мог бы подменить цены, и агент честно пересказал бы подделку.

**Валидация дважды.** Клиент проверяет расширение и размер для удобства,
сервер — повторно, включая проверку на бинарный файл. Клиентская проверка
никогда не считается защитой.

**Мобильная вёрстка проверена метриками, а не на глаз.** Скрипт
`scripts/audit-layout.ts` меряет реальное переполнение документа в
браузере. Первый прогон показал **167px горизонтального скролла** на
390px — таблица распирала страницу. Починено `minmax(0,1fr)` в сетке и
`min-w-[640px]` с локальным скроллом у таблицы. Сейчас 0px.

## Стек: LangChain + LangGraph

Клиент к polza.ai построен на `ChatOpenAI` с подменённым `baseURL` —
провайдер OpenAI-совместимый, поэтому весь код на стандартных классах
фреймворка, без самописного транспорта.

Что переведено на LangChain:

| Было | Стало |
|---|---|
| Самописный `fetch`-клиент с ретраями | `ChatOpenAI` (встроенные ретраи, таймауты) |
| Своя JSON-схема + ручной парсинг | `withStructuredOutput(zodSchema)` |
| Ручная сборка массива сообщений | `ChatPromptTemplate` + `.pipe()` |

Что **сознательно оставлено вне** LangChain: детерминированный матчер,
нормализация прайса, парсер смет. Там нет LLM, и заворачивать денежную
логику в LLM-фреймворк — значит потерять возможность тестировать её без
сети. LangChain владеет вызовами модели, а не бизнес-правилами.

## Агент (LangGraph)

Агент работает в двух режимах:

- **без сметы** — отвечает по прайсу («сколько стоит тройник 315/200»);
- **со сметой** — помнит загруженный документ и отвечает по нему
  («почему позиция 15 требует проверки», «какой итог», «что не вошло в сумму»).

```bash
node --env-file=.env.local scripts/agent.ts                    # интерактивный чат
node --env-file=.env.local scripts/agent.ts --demo             # демо с памятью сметы
node --env-file=.env.local scripts/agent.ts --load examples/estimate-office.txt
node --env-file=.env.local scripts/agent.ts --ask "какой итог?" --load ...
node --env-file=.env.local scripts/agent.ts --trace            # шаги графа
```

Команды в чате: `/load <файл>`, `/summary`, `/positions`, `/trace`, `/exit`.

### Граф

```
START → guard ─┬─(вне темы / инъекция)→ refuse → END
                └─(по теме)→ agent ◄─┐
                              │      │
                              ├─(есть tool_calls)→ tools ─┘
                              └─(нет tool_calls)→ END
```

Узел `guard` — дешёвый фильтр до вызова модели: ловит оффтоп и явные
инъекции регулярками, экономя токены (ответ за 5 мс вместо 3 с).
Узел `agent` решает, какой инструмент вызвать. `tools` выполняет вызовы
и возвращает управление агенту.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `find_item` | найти позицию и цену в прайсе |
| `list_by_type` | показать все размеры данного типа товара |
| `calculate_total` | посчитать сумму с учётом количеств |
| `estimate_summary` | сводка по загруженной смете |
| `estimate_positions` | позиции сметы, фильтр по статусу |
| `explain_position` | почему позиция без цены / получила цену |

**Ключевое архитектурное решение:** у агента НЕТ инструмента «задать цену».
Цена всегда приходит из прайса через детерминированный матчер. Даже
полностью успешная инъекция не сможет подменить цену — такого действия
просто не существует в API инструментов.

Арифметика тоже вне модели: сумму считает JS, а не LLM. Модель, которая
«посчитала в уме», рано или поздно ошибётся на порядок.

### Память сметы

Сессия (`src/lib/agent/session.ts`) хранит результат обработки — не сырой
текст. Цены фиксируются матчером при загрузке, и последующий диалог не
может их изменить: все инструменты сессии только читают.

Различаются два номера: `posNo` — номер позиции в КП (1, 2, 3…), его
называет человек, и `lineNo` — номер строки в файле (может быть 17, если
выше шапка). Агент не путает их в ответах.

## Архитектура матчинга: детерминизм → LLM → человек

```
строка сметы
     │
     ▼
[нормализация]  тип + размеры + угол + исполнение
     │
     ├── точное совпадение ──────────► ЦЕНА из БД   (LLM не вызывается)
     │
     ├── размера нет в прайсе ───────► "нет в прайсе" (LLM не поможет)
     │
     └── неоднозначно / не разобрано
              │
              ▼
         [LLM resolver]  structured output, только список кандидатов
              │
              ├── уверенность ≥ 0.85 и id существует ► ЦЕНА из БД
              └── иначе ─────────────────────────────► needs_human
```

Три уровня защиты, из которых работает хотя бы один:

1. **Архитектурный** — LLM не имеет доступа к ценам, только к списку id.
   Даже при успешной инъекции выдумать цену нельзя.
2. **Промптовый** — жёсткие правила, данные клиента отделены тегами.
3. **Кодовый** — постпроверка ответа: выдуманный id отбрасывается,
   пустое обоснование обнуляет уверенность, угадывание исполнения
   `(R)` при отсутствии его в смете блокируется принудительно.

## Расходы на LLM

Замерено на 27 строках трёх тестовых смет:

- LLM-вызовов: **4** (15% строк), остальные решены детерминированно;
- среднее время ответа: **~2 с**;
- стоимость: **~0.03 ₽** за прогон.

Именно поэтому гибридная архитектура важна не только для качества,
но и для экономики: наивный вариант «всё через LLM» стоил бы в разы дороже.

## Особенности реального прайса

Прайс содержит реальные аномалии, которые важно обрабатывать корректно
(подробности — в `fixtures.ts`):

- размерные ряды с «дырами»: Ø450 есть у врезки прямой, но нет у отвода и заглушки;
- двойные пробелы в названиях;
- позиции, стоящие не в своём месте списка (`Отвод сегментный 90 градусов 150`);
- немонотонность цен (`Муфта ф500` дешевле `ф450`);
- варианты исполнения `(R)` у штампованных отводов;
- **несимметричная запись размеров**: 21 из 29 врезок и 20 из 28 тройников
  записаны только в одном порядке (`160/200`), но клиент может написать
  наоборот (`200/160`). Для этих типов сравнение идёт по множеству размеров,
  для переходов — по порядку, так как направление важно.
